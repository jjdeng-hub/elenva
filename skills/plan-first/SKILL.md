# 先规划后动手

小改动（单文件、意图明确）直接做。**其余情况先出方案**——返工的成本远高于多花的两分钟。

## 什么时候必须规划

- 需求模糊：用户说"优化一下""帮我做 X"，但验收标准不清楚
- 改动面大：预计动 3 个以上文件，或涉及公共模块/接口
- 高风险：删除、迁移、批量重命名、动配置与凭据
- 用户明确说"先给方案 / 别急着动手"

## 怎么做

1. **只读勘察**：把要改的地方读明白（见 repo-recon 技能）。不要边看边改。
2. **写方案**，控制在 15 行内，只写影响决策的内容：
   - 要改哪些文件（具体路径）
   - 每步做什么、怎么验证（每步尽量可独立验证）
   - 风险与回退方式（有没有不可逆操作）
   - 不写背景复述、不写客套话
3. **拿批准再动手**（如果界面开了计划模式，用 `present_plan` 提交）。
4. **执行中偏离方案要说明**：发现新情况改路线，先说一句为什么。

## 计划模式与 plan 子代理

- 界面上开了「计划」开关时：只有只读操作可用，写完方案调用 `present_plan`，批准后自动解锁。
- 需要产出实施方案的调研，可以交给 plan 子代理（在对话里说"用 plan 子代理制定 XX 的方案"）。

## 反模式

- 一边勘察一边顺手改（方案就不成立了）
- 方案写成散文（用户要在弹窗里扫一眼看懂）
- 方案里写"预计 X 分钟"之类无法验证的话
