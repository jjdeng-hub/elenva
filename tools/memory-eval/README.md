# 记忆系统评估（memory-eval）

`pi-hermes-memory` 的**真实跑一遍**评估。回答同一个问题：

> 这次改动（注入策略 / 检索 / 整理 / 条目结构）有没有让 agent 更记得住、找得到？

## 依据

- 《深入理解 AI Agent》ch3 **L43「记忆能力的评估：三层次框架」**：基础回忆 / 多会话检索 / 主动服务。
- ch3 **实验 3-1** 的可操作流程：会话生成记忆 → 在「只能访问记忆、不可回看原始对话」下回答新问题 → **LLM-as-a-judge** 打分。
- ch3 **L221 / L505**（压缩整理、记忆更新）→ 本夹具的 **L4 容量压力**层：四份记忆文件长期贴顶（实测 99%），必须测「贴顶写入 + 整理后关键事实还在不在」。

## 怎么跑

```bash
node .audit/memory-eval/run.mjs                     # 全部用例（10 条，约 5-6 分钟）
node .audit/memory-eval/run.mjs --memory-layer legacy   # 对照组：pi-hermes-memory 全文注入
node .audit/memory-eval/run.mjs --layer L4 --repeat 3   # 带随机性的层重复采样，看成功率
node .audit/memory-eval/run.mjs --case l1-account --keep # 单条；--keep 保留沙箱好排查
```

`--memory-layer`（默认 `layered`）：`layered` = 沙箱切成 `policy-only` 并拷入
`extensions/elenva-memory` 扩展（双层记忆）；`legacy` = 原有全文注入。两者用同一份用例，直接可比。

报告落在 `reports/report-<时间>.json`（含逐条回答、判分理由、记忆文件用量），`reports/latest.json` 是最新一轮。
退出码：`0` 全部跑完；`1` 夹具自身出错（真实记忆被动过 / 沙箱起不来）；`2` 有用例超时或崩溃。
**分数不设通过线** —— 它是度量，不是门禁。

## 校准记录与基线（用例是调过的，不是随手写的）

第一版用例只有单事实、单会话，7 条全部 9-10 分（均分 9.9/10）——那是**测不出差别**的假绿：
全文注入 + 单事实，什么系统都能答对。现在这版刻意埋了三类难度：

1. **同类多项并存**（三台机器的 Node / 四个号码 / 两个项目的部署）——考检索精度，不是「记住了吗」；
2. **跨会话更新**（改主意、改计划）——考新旧覆盖与「计划 vs 已完成」的区分；
3. **容量贴顶 + 老条目**（L4）——考满仓时写入是否成功、整理是否丢掉埋在噪声里的关键旧事实。

L1 两条故意保持简单，当**回归地板**用：它们掉分就说明流水线坏了，而不是题目难。

### 双层记忆改造前后（2026-09-20，同一份用例、同一只模型）

| | legacy（全文注入） | layered（索引 + 检索） |
|---|---|---|
| 总体得分（10 条） | 10.0 / 10 | 10.0 / 10（第二次跑 9.9，差异在噪声内） |
| 常驻注入成本（均） | 2251 字符 | **665 / 683 字符** |
| 常驻注入成本（最大，容量贴顶那条） | 9372 字符 | **1640 / 1639 字符** |
| 关键事实落盘 | 10/10 ✓ | 10/10 ✓ |

→ 质量持平、**常驻成本降到约 30%（贴顶场景 17%）**。

`L5-detail-beyond-summary` 是专门为这次改造加的风险用例：关键数字被埋在长条目末尾（摘要看不到），
layered 模式下必须真的去检索取原文 —— 实测 10/10，且扩展的 `state.json` 录到
`toolCalls: {memory_find: 1, memory_search: 1}`（先用自己的重排检索，不够再用包自带的），
以及 `evidence` 记下了每条是哪个工具、何时写下的（L505 的「从哪条证据而来」）。

一个可观察的副作用：改造后 `l2-deploy`（跨会话更新 + 项目串味）从首轮的 6 分提到 9-10 分 ——
新旧两条不再被当成「无法确定的矛盾」，而是「一条已变更、一条待确认」。

### 基线：2026-09-20（改造前，legacy 全文注入，9 条用例）

| 指标 | 数值 | 读法 |
|---|---|---|
| L1 基础回忆 | 10.0（2 条） | 流水线正常，回归地板 |
| L2 多会话检索 | **8.7**（3 条） | 唯一失分处，见下 |
| L3 主动服务 | 10.0（2 条） | 护照、过敏两个主动提醒都做到了 |
| L4 容量贴顶 | 10.0（2 条，`--repeat 3` 也 3/3 满分） | 满仓写新事实没失败 |
| 总体 | 9.6 / 10 | 天花板效应：单事实问答已无区分度 |
| 关键事实落盘 | 9/9 ✓ | 确定性指标，不靠判分模型 |
| 常驻注入成本 | 均 2159 字符，最大 9375 | **双层架构改动的主要收益侧**（分数不掉、这个数该明显变小） |

两个实测结论（都推翻了先前的推测，这就是评估的价值）：

> 口径提醒：上表是首轮实测的数字。同日后来的对照跑里 l2-deploy 两次都是满分 —— 那条跨条目矛盾
> 是**间歇出现**的行为（取决于模型写入时把两条事实写成什么样），不是稳定失分。单次分数别当结论用。
- **满仓不等于写不进去**。四份存储全贴顶（MEMORY 3982/4000、USER 2448/2500、项目 2951/3000）时，
  新事实仍能落盘并可回答（`--repeat 3` 全过）——系统会腾地方（删除/合并噪声条目）。
  所以「容量」问题的真正代价不是记忆丢失，而是**每轮要背的常驻内容越来越多**，以及下述的跨条目矛盾。
- **真正的失分点是「旧条目没跟着更新」**：`l2-deploy` 第二问只拿 2 分。会话 2 写下的条目是
  「项目 alpha2 与 alphawork 采用相同策略：保持便携包、不引入 Docker」，会话 3 把 alphawork 改成 Docker，
  **这条旧条目没有被重写** —— 提问时 agent 同时读到两条互相矛盾的说法，只能回答「无法确定」。
  对应书里 ch3 **L505**（增量更新要「先检索相关已有知识再增删改」，以及定期全量整理的冲突解决与场景限定）：
  我们现在只有「溢出才合并」，没有周期性重审，也没有条目间的引用/主体字段。

## 口径（读分数前先读）

| 环节 | 我们怎么做 | 为什么 |
|---|---|---|
| 生成期 | 每个会话一次 `pi -p`，末尾附一句「请把值得长期记住的用户信息写入记忆，然后回复 SAVED」 | 这是实验 3-1 的「记忆生成」步骤；测流水线（写入→存储→注入→检索→整理），不测 agent 记录的自发性 |
| 隔离 | 会话之间只靠「记忆」通道；提问前删掉 `sessions.db*` | 书要求「不可回看原始对话」；顺带堵住 `session_search` 兜底 |
| 提问期 | 只发原句问题，不加「请先检索记忆」的暗示 | 否则会掩盖「该检索却没检索」这类真实问题 |
| 判分 | 另一个 LLM 按用例自带 `criteria` 打 0-10，只看事实一致性 | 与书一致（LLM-as-judge）；细则写进用例，避免口径漂移 |
| 模型 | 默认取 `~/.pi/agent/settings.json` 的默认 provider/model | 与日常使用同一只模型 |

**已知偏差**：① 单次采样，分数受随机性影响（同一版本建议跑 2-3 次看均值，别拿单条 1 分之差当结论）；
② 生成期末句提示会让记忆写入比日常更「勤」——所以分数反映的是**流水线能力上限**，日常实际会更差一些；
③ 判分模型与执行模型同源（要独立评审需 `--judge-model` 指定另一家）。

## 安全

- 沙箱在系统临时目录，`PI_CODING_AGENT_DIR` 指向它；记忆目录叫 `store/`（**不能**叫 `<agentRoot>/memory` —— 那是扩展的 legacy 根，会被迁移合并，实测踩过）。
- 运行前后各取一次真实 `~/.pi/agent/pi-hermes-memory/*.md` 的 mtime+size 快照，**变了即判 FAIL**。
- 评估只加载 `npm:pi-hermes-memory` 一个包（沙箱 settings.json），不加载其余扩展。

## 加用例

改 `cases.json`：

- `sessions[].turns`：生成期会话原文（按顺序跑，会话之间只有「记忆」这条通道）；
- `questions[]`（或单条 `question` + `reference` + `criteria`）：提问期与判分口径；一条用例可多问，用例得分 = 各问均分；
- `setup.prefill` + `setup.padToChars` + `setup.prefillAgeDays`：直接铺一批「历史记忆」（不经模型，用来造容量压力；`padToChars` 会按模板补到指定字符数，`prefillAgeDays` 让条目显老，诱惑整理把它们当陈旧条目清掉）。

层（`layer`）目前有 L1 / L2 / L3 / L4 / L5：前三层对应书里的三层次框架，L4 是本仓库自加的容量层，
L5（`l5-detail-beyond-summary`）是双层记忆的**风险面专测**：关键细节在摘要之外，不检索就答不出
（legacy 全文注入下无条件答对，所以它只对 layered 模式有区分度）。
