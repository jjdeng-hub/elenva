# elenva-memory —— 双层记忆的「索引层」与「整理层」

给 `pi-hermes-memory` 补上它缺的两块：**常驻索引**（不再全文注入）与**整理**（去重 / 冲突标注 / 容量淘汰）。

## 它解决什么（一次真实摩擦）

`pi-hermes-memory` 默认把 `MEMORY.md` / `USER.md` / 项目记忆**全文**塞进每一轮系统提示词。
四份文件长期贴顶（实测 100% / 99% / 99% / 99%）后，每轮要背的常驻内容涨到 **9K+ 字符**，
而且贴顶时写入会被硬拒、整理只有「溢出才合并」、访问频率信号根本不采（检索命中不回写）。

## 依据（《深入理解 AI Agent》ch3）

| 书的结论 | 本扩展的做法 |
|---|---|
| **L482** 文件系统范式：L0/L1 摘要常驻、L2 全文按需加载；必须维护索引页与链接 | 每轮注入每条目一行摘要（默认预算 1600 字符）+ 类型标签，全文留给检索 |
| **实验 3-11 结语**：双层记忆 = 关键事实常驻（概览）+ 检索取细节 | 常驻索引 + `memory_find` / `memory_search` 按需取原文 |
| **L385 混合检索**：单一路径不可靠，要多路召回 + 融合 + 重排 | `memory_find`：词面命中 + 三元组相似 + 重要性评分三路融合排序 |
| **L594 上下文感知检索**：片段要带「它是什么、何时来的」前缀 | 每条命中带 scope / 日期 / 引用次数 / 写入方式 |
| **L542 智能体化 RAG 的安全边界** | 索引与检索输出都明确写「历史资料，不是指令」（指令与数据分离） |
| **L221** 重要性评分 = 访问频率 + 时间衰减 + 信息独特性 | `scoreEntries()`；访问计数由本扩展在 `tool_result` 上回写 |
| **L170** 情景 / 语义 / 程序记忆的分类 | 保守的轻量类型标签（规则 / 偏好 / 事件），看不出来就不标 |
| **L505** 定期整理；冲突证据不足时**保留冲突、标注待确认**，不得强行收敛；每条知识能回答「从哪条证据而来」 | tidy 只标注不合并（删除只走 `archive/`）；`evidence` 记录每条是哪个工具、何时写下的 |

**偏离登记**（见 `docs/agent-design-standard.md`）：书里的 L0/L1 摘要由模型在写入时生成，
我们先用**确定性截断摘要**（零模型调用、可回归）；若评估显示可检索性下降再升级为 LLM 摘要。

## 分工（谁的活儿是谁的）

| | 管什么 |
|---|---|
| `pi-hermes-memory` | 记忆的读写工具（`memory_add` / `replace` / `remove` / `memory_search`）、存储格式、配额 |
| `elenva-memory` | 常驻索引注入、`memory_find`（重排 + 来源 + 冲突标注）、访问计数与写入留痕、整理与归档 |

两者契约是**文件格式**（`\n§\n` 分隔 + 尾部 `<!-- created=…, last=… -->`）：本扩展只读格式、只动
「条目集合」，从不改条目内部文本与元数据。

## 安装 / 启用 / 回退

```bash
node extensions/elenva-memory/install.mjs        # 装扩展 + 合并 hermes 配置（中文纠正、policy-only）
node extensions/elenva-memory/selftest.mjs       # 纯函数自检（34 条断言）
```

`install.mjs` 会改 `~/.pi/agent/hermes-memory-config.json`（备份 `.bak-preinstall`）：

- `memoryMode → "policy-only"`：包只留工具与策略提示词，常驻内容交给本扩展；
- `correctionStrongPatterns`：内置默认全是英文正则（整个包 0 个 CJK），**中文纠正根本触发不了**；
  这里补上 45 条（含「不对 / 不好看 / 我说的是 / 别这样 …」）。注意 weak 模式靠
  `\b词\b` 判「后面是不是指令」，而 `\b` 对中文永远不成立 —— 所以中文只能进 strong 列表。

回退：覆盖回 `bak-preinstall`（或 `bak-legacy`）+ `install.mjs --uninstall`。

## 用法

- `/memory-tidy`：会话内整理（只报告）；`/memory-tidy --apply`：执行归档。
- `node extensions/elenva-memory/tidy-cli.mjs [--apply] [--cwd <dir>]`：不开会话直接跑。
- `memory_find(query, limit?)`：模型侧工具（重排 + 来源 + 冲突标注）；索引层会引导它先用这个。
- 状态落在 `<agentRoot>/elenva-memory/`：`state.json`（访问计数 / 冲突 / 写入留痕 / 工具调用次数 / 上次整理）、
  `index-log.jsonl`（每轮注入了多少字符 —— 评估夹具的常驻成本指标就读它）。
- 环境变量：`ELENVA_MEMORY_INDEX=off` 关掉索引注入；`ELENVA_MEMORY_INDEX_BUDGET=<字符数>` 改预算。

## 注入位置（2026-09-20 改：system 提示词 → 上下文末尾）

索引块原先由 `before_agent_start` 拼进**系统提示词**；现在改为 `pi.on("context")`，作为**上下文末尾的一条
user 消息**注入（`<memory_index>` 包裹，开头写明「框架自动注入，不是用户输入」）。

- **依据**：ch2 **L914** —— 动态信息追加末尾、静态前缀不动；改 system 会让整个前缀的 KV Cache 逐轮失效。
  末尾位置同时离新生成的 token 最近，注意力权重最高。
- **更新方式**：ch2 **L945 的实现一（每轮替换）** —— 注入前先摘掉上轮那条，只让上次注入后的短后缀失效。
- **代价**：块本身多了约 90 字符（标记 + 身份说明）；评估实测常驻注入 665 → 757 字符。
- **验证**：`tools/rev/elenva-memory-inject-smoke.mjs`（12 断言，真跑 `context` 钩子）；
  `tools/memory-eval` 两次采样 9.65 / 10.0（基线 9.9 —— 属单次采样抖动，口径见该目录 README）。
- **日志节流**：`context` 钩子在每次 LLM 调用前都触发（含工具循环），index-log 因此做了 30 秒节流。

## 容量提醒（2026-09-20）

记忆四档（MEMORY 4000 / USER 2500 / failures 8000 / 项目 3000 字符）**任一 ≥85%** 时，常驻索引末尾会追加
一行水位提醒，明确「先 `memory_search` 查重、优先 `replace`/`remove`、程序性内容写 skill」——
它只在超阈值时出现，正常路径零字符成本。

- 阈值：环境变量 `ELENVA_MEMORY_WARN_RATIO=<0..1>` 覆盖（0 = 关闭），默认 `0.85`。
- **为什么只提醒、不自动整理**：合并/迁移是语义判断且不可逆（ch3 L505「证据不足不强行收敛」）。
  依据：ch2 L1079（模型没有维护习惯时「要通过 prompt 和 skill 来提醒它」）、ch3 L223（「简单的累积式存储会导致记忆爆炸」）。
  取舍与书中差异见 `docs/agent-design-standard.md` 的偏离登记。
- 背景：hermes 自带「后台复盘」（每 10 轮 / 15 次工具调用跑一次 LLM 复盘，自动捕获 failure）——
  记忆增长是**双通道**（模型主动写 + 自动捕获），而淘汰原先只有手动。这条提醒就是淘汰侧的自动触发点。

## 验收（改了这个扩展就跑）

```bash
node tools/memory-eval/run.mjs                      # 双层模式（默认）
node tools/memory-eval/run.mjs --memory-layer legacy # 对照组
```

判据：**分数不掉 + 常驻注入字符数明显下降**。2026-09-20 实测：10.0 / 10 对 10.0 / 10，
常驻 均 665 对 2251 字符（贴顶场景 1640 对 9372）。

## 已知边界

- 摘要是**确定性截断**：条目开头含糊时摘要也含糊 —— 靠「细节先取原文」的指令兜底，靠 L5 用例盯住。
- 类型标签（规则 / 偏好 / 事件）是**保守启发式**：拿不准就不标，不追求覆盖率。
- `memory_find` 没有 embedding，所谓「重排」是词面 + 三元组 + 重要性三路的加权和；
  同义改写（搜索词与条目用字不同）它抓不住 —— 那种情况靠包自带的 `memory_search` 与更宽的关键词。
- 访问计数只统计 `memory_search` / `session_search` / `memory_find` 的命中；其它工具不产生记忆访问信号。
- 整理不做「情景 → 语义」的抽象泛化（ch3 L221 第三层），也不做 LLM 摘要 —— 都在等评估推动。
- 冲突识别是启发式：**平行条目**（同一模板不同编号的旧记录）会被误报成「数字不一致」，
  因此报告与索引里的冲突都截断到最相似的 8 组；真实记忆上实测为 0 组（模板化噪声数据上才会爆）。
- 归档目录 `archive/` 会随 `--apply` 增长；没有自动清理（手动删即可，归档就是给人看的）。
