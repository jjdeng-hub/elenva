# elenva-worklog —— Agent 的「工作记录」（情景记忆的当前段）

给 ELENVA 补上「我们这轮在做什么、做到哪一步、验证过什么」的持久载体。

## 它解决什么（一次真实摩擦）

用户问「怎么样了？到哪一步了？」时，agent 只能**现场口述** —— 没有持久载体；会话一压缩，
「我们做到哪了」就丢了。记忆（pi-hermes-memory + elenva-memory）管的是跨会话长期有效的事实与教训，
不承载进行中的工作。（旧的 pi-memory 有 SCRATCHPAD 层，换到 hermes 后这一层没了。）

## 依据（《深入理解 AI Agent》ch2 L851「Agent 状态栏：通过元信息增强 Agent 轨迹管理」）

| 书的结论 | 本扩展的做法 |
|---|---|
| **L855** 状态栏 = Agent 框架持续注入的**状态摘要**（任务进度/环境/计数），模型每轮「瞥一眼」 | 每轮注入最近一条工作记录 + 未完成待办 |
| **L861** 上下文学习更像检索而非推理，模型不会自动把轨迹归纳成结论 → 把隐式状态提炼成显式知识 | 写入时由 agent 提炼成结构化字段；注入只读第一条，成本恒定 |
| **L914** 位置：作为 **user 消息追加到上下文末尾**，不是改 system（改 system 会破坏整个前缀的 KV Cache） | 用 `pi.on("context")` 钩子追加 |
| **L945** 两种实现：每轮替换 / 持久追加，各有缓存代价 | 实现一（每轮替换）：注入前先摘掉上轮那条，只失效「上次注入之后新增的后缀」 |
| **实验 2-8** 带状态栏后每次迭代的思考 token / 延迟 / 花费降约一个数量级 | 状态块 ≤ 320 字符，超预算逐段收缩（先砍待办再砍标题） |
| **L902** 构成：任务规划 / 侧信道信息 / 环境状态观察 | v1 只做「任务规划」；工具调用计数等出现真实摩擦再加 |

## 与记忆的分工（ch3 L170 的三类记忆）

| | 管什么 | 容量 |
|---|---|---|
| 记忆（hermes + elenva-memory） | **语义记忆**：跨会话长期有效的事实、偏好、教训 | 有界（4000 字符），满了要合并 |
| 本扩展 | **情景记忆的当前段**：进行中 / 刚完成的工作 | 滚动窗口 20 条，溢出进 `archive/` |

上下游关系：工作记录承载原始过程与验证证据 → 整理时把值得长期留下的**提炼**进记忆，
不必什么都往 4000 字符里塞。

## 用法

- `worklog_write(title, goal?, did?, evidence?, todo?, status?)`：一段工作收尾时记一条
  （`status`: `done` 默认 / `doing` / `blocked`）
- `worklog_read(tail?)`：读最近的工作（接手长任务、被问「做到哪了」时用）
- `/worklog`：用户查看；`/worklog --all` 看全部
- 存储：`<agentRoot>/worklog/<项目名>.md`（最新在前），归档在 `worklog/archive/`
- 环境变量：`ELENVA_WORKLOG_STATUS_BUDGET`（默认 320 字符，`off` 关闭注入）、`ELENVA_WORKLOG_DIR`（改存储目录）

## 安装 / 验收

```bash
node extensions/elenva-worklog/install.mjs    # 装到 ~/.pi/agent/extensions/elenva-worklog/
node extensions/elenva-worklog/selftest.mjs   # 纯函数自检
```

## 已知边界

- 状态注入只带**最近一条**：更早的要 `worklog_read`（换来的是注入成本恒定）
- 不做工具调用计数（实验 2-9 的另一类技术）—— 等出现「反复调用同一工具」的真实摩擦再加
- 「每轮替换」意味着会话历史里不保留旧状态：陈旧状态不累积，但要看历史得读文件
- 扩展在**会话创建时**加载：装好后要新开会话才生效
