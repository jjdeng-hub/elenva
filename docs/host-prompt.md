# 宿主提示词：收录规则与维护流程

**什么时候读这份**：给这个 agent 加/改能力时；或者任何一次想动系统提示词之前。

> 为什么放在 `docs/` 而不是 `.pi/skills/`：`.pi` 下的资源会要求**项目信任**，
> 而信任会阻塞输入、且「有活跃会话时无法授予」（本仓库永远有活跃会话）。
> 一个纯 markdown 的约定不该触发那道闸门。发现入口在 `AGENTS.md` 的「常见任务」。

系统提示只有四块拼成，改动前先确认你改的是哪一块 —— 改错地方是这个仓库最容易犯的错。

## 一、三层地图（别改错层）

| 层 | 文件 / 位置 | 生效范围 | 谁维护 |
|---|---|---|---|
| pi 基座 | 内核 `core/system-prompt.js` | 所有 pi 会话 | **pi，我们不碰** |
| **宿主层** | `lib/host-prompt.ts` → `appendSystemPrompt`（身份段 + 环境事实） | Web 工作台打开的**每一个**会话 | 我们 |
| 项目上下文 | `<cwd>/AGENTS.md` | 该项目 | 用户 / 项目手写 |
| 技能 | `<name>/SKILL.md` | 按需 read，不占每轮预算 | 按技能 |

另外两处**不需要改代码**的插槽（只对 pi 生效，不随产品走）：

- `~/.pi/agent/APPEND_SYSTEM.md` —— 本机所有项目
- `<项目>/.pi/APPEND_SYSTEM.md` —— 该项目（会触发项目信任）

装配顺序（`core/system-prompt.js:buildSystemPrompt`）：

```
基座 → [宿主层] → pi 文档指针 → <project_context>AGENTS.md</project_context> → 技能索引 → cwd
```

## 二、收录判据：三条全中才写进宿主层

1. **agent 推断不出来** —— 读代码、试一次也拿不到的**宿主事实**。
   反例：「这个项目用 TypeScript」它 ls 一下就知道。
2. **知道了会改变行为** —— 不是背景介绍。
   反例：「ELENVA 是一个 Web 工作台」（它不改变任何动作）。
3. **对每个会话都成立** —— 不依赖具体项目、不依赖当前模式。
   反例：「本项目验证命令是 npm test」→ 那是 AGENTS.md 的事。

**更硬的判据：先问「这条能不能被 hook 保证」。** 能保证的（审批会拦、计划模式会拒），
提示词里只需一句「存在这回事」，别展开写规则 —— **提示词会被忽略，hook 不会。**
提示词负责「事先知道」，hook 负责「保证结果」，两者不是替代关系。

**身份段（`id: "identity"`）是形式上的例外，不是判据的例外。** 它不是「宿主事实」，
而是 agent 的自我认知：它叫什么、工作台是身体还是环境、岗位是什么、短板怎么上报。
仍然要过上面三条 —— 不写会有三个可观测的后果：把护栏当阻碍（而非自己的机制）、
界面上的机制（记忆 / 技能 / 插件）想不起来用、能力不足时只会笼统说「做不到」。

身份段有一条额外禁令：**不要写成表扬。**「你很卓越、你会自我提升」这类描述性身份
会引发表演性行为（模型开始说漂亮话，而不是做事）。写成「你的零件有哪些、做不到时
缺哪类、往哪升级」。

## 三、加能力时的清单

新加一个能力（工具 / 拦截 / 自动行为），按顺序过：

- [ ] agent 需要**事先**知道它吗？不知道会怎样 —— 撞墙浪费一轮，还是只是少用一次？
- [ ] 需要的话，写成 `HOST_PROMPT_SECTIONS` 的一段，填三样：
      `id`（稳定标识）、`rationale`（**为什么必须存在**）、`relatedTo`（哪个能力，方便回访）。
- [ ] 是否更适合别处？工具用法 → `promptSnippet`/`promptGuidelines`；项目规则 → `AGENTS.md`；
      流程知识 → 技能；动态状态 → hook 注入消息。
- [ ] 长度：**身份段 ≤ 700 字符、每条事实 ≤ 120 字符、整层 ≤ 1100**。每轮都注入，
      按 token × 轮数计费 —— 加东西前先想「删掉哪一句」。
- [ ] 措辞：命令式、说清「被拦下怎么办」。不要写「你应该」「请注意」这类没有约束力的句式。
- [ ] 跑 `node ./node_modules/typescript/bin/tsc --noEmit`（这一段是代码，不是文档）。
- [ ] 跑夹具：`node --experimental-strip-types tools/rev/host-prompt-fixture.mjs`
      （形态 / 顺序 / 拼接 / 关键句 / 长度预算，23 项全绿才算过）。
- [ ] 要更接近真实：开一个新会话，确认 `/api/sessions/<id>/state` 的 `systemPrompt`
      里有 `## 你是谁`（身份段）与 `## 运行环境（ELENVA Web 工作台）`（事实），
      位置都在基座之后、`<project_context>` 之前。
- [ ] 想一下**度量**：这个能力上线后，哪个数字应该变？（见第五节）

## 四、两个反模式

**1. 别把动态内容塞进系统提示。** 系统提示是前缀缓存的第一个块 —— 改一个字，
整段对话的缓存全失效。现在的计划模式用 `before_agent_start` 返回
`event.systemPrompt + PLAN_MODE_PROMPT`，属于「接受代价的例外」（临时模式、那段时间在勘察），
但不要把这种写法推广。会变的东西走 `pi.sendMessage(..., { triggerTurn: true, deliverAs: "followUp" })`
（收尾验证追问就是这么做的）。

**2. 别在宿主层写项目知识。** `AGENTS.md` 已经 3800+ 字符且每轮注入，用户的团队靠它写项目约定；
宿主层写项目知识就变成「一份对所有人都错的提示词」。宿主层只写「跟这个工作台有关、跟项目无关」的事实。

## 五、度量：怎么知道这层有效

别凭感觉。这个仓库已经有现成的口径：

| 改了什么 | 该看哪个数字 | 数据源 |
|---|---|---|
| 身份段（范围宽 + 短板上报） | 「这不像编程任务」式推辞、笼统的「做不到」 | 会话文件 |
| 收尾要有证据 | 「改了代码但无证据」的追问率应下降 | `~/.pi/agent/elenva-verification.jsonl` + 追问记录 |
| 危险操作会被拦 | 被拒后**原样重试**的次数应下降 | 审批拒绝记录 + 后续同类 `tool_call` |
| 无终端交互 | 「需要关注」里的工具报错应减少 | `/api/attention` |
| 计划模式 | `present_plan` 的调用率、被批准率 | 会话文件里的工具调用 |

## 六、查看与调试

- 界面：设置页 → **宿主提示词**（只读，含每段 rationale 与装配顺序）
- 接口：`GET /api/host-prompt`
- 真实结果：`GET /api/sessions/<id>/state` → `state.systemPrompt`
- 若怀疑没生效：先确认这个会话走的是**普通分支** —— 纯对话（chat-only）与子代理
  （`subagentResources`）**不注入宿主层**，因为它们没有工具、也没有护栏与快照
  （对它们说「你的改动有快照」是撒谎）。加能力时若该能力对子代理也生效，
  要同时把这段提示词加进子代理路径（`lib/subagent-prompt.ts`）。
