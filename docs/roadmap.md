# ELENVA 路线图（2026-09-21 定）

> 定位（一句话）：**给一个人用的 Agent 驾驶舱** —— 把不确定的 agent 关进可观察、可接管、可回滚的界面里。自用优先（详见 `AGENTS.md` / `README.md`）。
> 本文只记方向与触发条件；具体安排随做随调。

## 三阶段顺序（2026-09-21 定）

### 1. 做深（当前阶段）
把桌面驾驶舱做扎实：观测、治理、**维护视角（"发动机舱"进 UI）**。
候选（按推荐顺序）：
- **系统页**：服务状态 / 门禁（elenva-gates）/ 备份（最近快照）/ 内核与 CLI 版本对齐 / 部署信息 / 资源水位。（✅ 2026-09-21 上线）
- **观测的时间维度**：周报（花费、会话、异常，轻量投递）。（✅ 2026-09-21 上线：`elenva-weekly` cron，周一 08:30 追加到飞书周报文档）
- **设置页对齐内核新能力**（如 0.86 缓存保温模式，小项）。（✅ 2026-09-21：设置页新增 cacheWarming 三档）

### 2. 做远（做深之后）
随身入口（手机 / 外网）。若走：信息架构围绕「需要你处理的 + 审批 + 状态」重做，**不是响应式 CSS**。
- 触发条件：真的想在外面处理 agent。
- 前置：云厂商安全组放行 8446（TCP，在控制台操作）。

### 3. 做广（最后）
从"看清"到"编排"：多 agent 调度台（并行试验 / 子代理监控是种子）。
- 触发条件：自动化 agent 舰队真的出现（目前这类活在 Hermes cron 里）。

## 明确不做（除非定位重估）
- 产品税旁支（见下方「开源姿势」）：不做多用户 / i18n / 上手引导类产品功能；不承担支持义务；发布只走 GitHub Releases。
- 响应式 CSS（不解决"做远"的问题）。
- 写作 / 社交 / 美化类功能（新功能一票否决题：是否服务"看清与接管"）。

## 开源姿势（展示式；2026-10-09 修订）

**为什么开源**——不是为「服务用户」，是为三个只属于作者自己的回报：

1. **作品与信任**：不公开的软件是私人物件；公开且真在跑的软件才算「作品」。「一个人 + 一个 agent 系统当操作系统用」——市面上 demo 很多、真在跑的很少，稀缺品要摆出来才成立。
2. **回声**：北极星是「真实收成（有人用/问/参与）」。回声结构上要求外部能接触项目——闭源即恒为零；开源让回声有从 0 到 1 的可能（哪怕只是一次 star、一个 issue、一句「怎么跑」）。
3. **内容实物**：「边造边给人看」需要一个能看的实物，开源仓库就是它；同时它是防「自嗨的虚假」的锚——让项目接受现实检验。

**边界（「考虑用户」的三层拆分）**：

- 功能层：**不为陌生用户设计**——不做多用户 / i18n / 上手引导类产品功能。
- 通道层：**让想跑的人跑得起来**——「想跑就自己跑」的通道保持通畅（`启动.cmd` / GitHub Releases / README）；这是给回声留门，不是服务承诺。
- 运营层：**不承担支持义务**——不承诺答疑、不为不想跑的人铺路。

「为我而生 → 因我不同 → 引同类来」——「引」的前提是「可见」；不追用户，但同类要能找到。

- 发布与更新只走 **GitHub Releases**（npm / 便携包通道已于 2026-10-08 废弃删除）；发布约定见 `docs/release.md`。
- 定位不变：「给一个人用的驾驶舱」；不翻案多用户 / i18n / 支持体系。
- 就绪状态：隐私审计 ✅（全历史扫描）/ CI ✅ / 转 public ✅（2026-09-25）/ 发布 ✅（`v0.1.0` → `v0.1.1`，首个 GitHub Release 2026-10-08）。
